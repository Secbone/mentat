# 首次统一评测：预检修复与受控试点

日期：2026-10-16。真实模型为 OpenCode ACP 的 `opencode-go/deepseek-v4.1-flash`，OpenCode 2.0.25。已完成 108 个纵向任务、12 道公开阅读题；显式记忆的内容使用有效，输出格式仍不稳定，逐任务反思尚未体现新增收益。本轮为小样本、非盲诊断，不构成公开榜单成绩。

## 冻结的协议

原生纵向试点包含家庭管理、财务分析、软件工程三类任务，每类两个独立用户，共六个档案。每档案六个任务：明确学习、迁移、单次例外、恢复默认、明确更新、更新后的新任务。三个对照组均接收相同可见输入，学习与更新回合均按用户原文确认类型；reset 每任务清空状态，explicit 跨任务保留显式记忆，reflect 在同样记忆基础上逐任务反思。

共 108 个任务，调用上限 180 次、每轮超时 90 秒、每组每档案仅重复一次。任务与评分在运行前冻结；评分规则、未来任务和参考答案不传入 subject。所有组拒绝工具权限，使用独立工作目录和新会话。该设置验证宿主上下文与记忆行为，不验证工具检索或执行能力，也不是文件系统沙箱。

分别检查任务数值/字段、约束遵循、格式偏好、偏好更新、例外恢复和纠正次数。只有首次迁移任务允许按失败触发一次纠正，主要指标始终检查首答。JSON 检查要求整个回答可解析；格式失败会同时影响字段检查，不能直接把零分解释成算术错误。复核时须区分缺少历史规则导致的合理澄清、错误业务答案、格式不合规和工具协议文本泄漏。

反思提案保持候选，不自动激活。因此 explicit 与 reflect 的业务成绩相近并不证明反思没有价值；本轮能观察的是反思可执行性、候选质量/重复、污染、额外成本，以及是否损害已有规则。不能以候选数量增长证明学习有效。

公开集使用 [LongMemEval 官方 cleaned 数据](https://github.com/xiaowu0162/LongMemEval)中的 Oracle 文件：仅保留证据会话，按时间排序后将 role/content/date/id 作为引用材料。清除 has_answer 等标签，参考答案仅留在评分侧。每种 question_type 按 question_id 排序选前两题，共 12 题，不根据输出挑题。原文件 500 题，HF 元数据版本为 `98d7416c24c778c2fee6e6f3006e7a073259d48f`；实际下载字节摘要固定在计划中，元数据查询晚于下载，内容身份以摘要为准。

这组测的是拿到证据后的阅读能力，未模拟历史写入、遗忘或检索，不是完整 LongMemEval。官方评估使用语义裁判；本轮精确匹配仅作为保守屏查，另做逐题非盲语义复核，不能当作官方正确率。原始数据、参考答案和完整对话保留在本机忽略目录。

每组 36 个任务，其中 12 个为学习/更新，无业务评分；24 个检查首答。六个档案的评分任务数相同，以下比例也等于任务族宏平均。括号为通过数/有评分任务数。

纠正仅针对每档案首个迁移任务，最多六次/组；这些数不能解释成自然用户的总体纠正率。反馈通常仍输出代码围栏，导致“字段正确但严格修复失败”。reset 不具备此前规则，部分回答合理地澄清缺失信息；低分代表该受控请求未完成，不能据此声称它不会做算术。

组内配对覆盖完整，explicit 相对 reset 的任务字段差值为 +33.33 个百分点；reflect 相对 explicit 为 -8.33 个百分点，六档案 bootstrap 95% 区间为 [-41.67, +20.83] 个百分点。后一个区间包含零，加上格式耦合和每组仅一次运行，不能认为反思已经提升或损害业务能力。配对记录和趋势导出保存在本轮集合目录中。

### 事后诊断：大部分失败来自格式

不更改主分，额外只允许移除包住整个回答的单一代码围栏，再使用原有字段规则检查：

| 诊断 | reset | explicit | reflect |
|---|---:|---:|---:|
| 24 个评分首答中的非严格 JSON 数 | 23 | 15 | 17 |
| 可仅去围栏恢复的回答数 | 2 | 15 | 16 |
| 严格解析或仅去围栏后，任务/约束/偏好均正确 | 2/24 | 24/24 | 23/24 |

reset 的任务字段单项可通过 3/24，但其中一个回答不满足约束，因此三项同时正确仅 2/24。reflect 剩余的 `engineer-1-5` 在 JSON 块后添加解释，自动围栏恢复器明确不接受；逐条复核发现其中字段也正确。由此，保留记忆的两组在本次用例中都能使用正确内容，但输出契约不稳定。该检查由当前分析助手完成、非盲，见[复核记录](../../benchmarks/pilots/2026-10-16/longitudinal-review.json)，不替代主成绩，也不证明普遍正确率达到 100%。

另有首答直接输出 DSML `memory_search` 调用文本的情况。代表样本 `reset/household-1-1` 的记录中没有对应工具执行或权限事件，不能把这些文本当作成功检索。宿主政策引导使用记忆工具，而本轮工具权限固定拒绝；引擎工具封装、权限策略与提示之间的实际匹配需要专项验证，当前证据不足以只归因于模型或某个适配器。

### 反思与记忆审计

36 次反思均 completed；新增 0、合并 0、跳过 10、拒绝 0，无传输异常。候选未激活，已确认规则常被判断无需再保存。108 份记忆后快照中，没有发现非用户 basis 的激活记忆、激活记忆来源字段违规，或将引用中的“别人的格式”激活为用户规则。该审计仅覆盖本批样本及所列条件，不等同于通用语义来源安全证明。

reflect 费用为 explicit 的约 3.54 倍，中位耗时约 2.62 倍；这批已显式确认规则的短任务没有产生新候选，不能证明默认每任务反思值得其开销。也不能据此否定反思，因为本轮缺少反复纠正、失败经验、隐含方法归纳与审核激活场景。没有自动修改代码、训练参数或跨代自改，不能称作 RSI 提升。

## 下一轮优化顺序

1. **先修输出契约。** 在宿主提示与响应处理层明确 JSON 约定，保留原始正文、解析状态和校验反馈；纠正时直接指出代码围栏/附加说明的问题。这次大多数内容已经正确，优先改善交付可用性。仅修改被测宿主后，可以使用本批冻结输入和主评分做配对回归。
2. **拆开格式与业务指标。** 下一版协议将严格格式、业务数值、约束、偏好分别计分，增加格式失败的已知正反例。若改题目或评分器，升级 dataset/scorer/protocol，重新建立基线，不能把新旧分数直接算成提升。
3. **校准工具提示和权限。** 为拒绝工具、只读记忆工具允许、execute 包装映射分别建立小型契约案例，要求工具事件、权限结果和最终回答一致。未验证前保持权限边界，不能为跑分整体放开 execute。
4. **反思改为有证据触发，并补充可学习任务。** 测试重复纠正、可复用失败经验、跨领域方法迁移和噪声；单列有用候选精度、证据正确率、重复率、更新延迟、审核成本及激活后的保持率。先与逐任务反思做冻结对照，不仅比较新增数量。
5. **继续接公开上游协议。** LongMemEval 增加真正的历史摄入/检索与拒答；为语义裁判提供正确、错误、部分正确的校准样本，使用原始 scorer 核对。之后按框架清单推进 PAST、PersonaMem、工具/安全环境和技能/自改集。当前其余公开集仍是待桥接状态，不能标记成已跑通。

本轮支持“显式确认后的规则可跨任务使用、当前主要交付问题是格式、逐任务反思存在可见开销”三个判断。尚未证明隐含偏好学习、长周期有效期、拥挤检索、真实工具操作、独立专业正确性、审核后自动学习和递归自改能力；本次 DeepSeek/OpenCode ACP 结果也不能外推为 Pi 的效果。
