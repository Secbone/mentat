## 建议结论

优先补齐三条链路：**确认后的规则能保留正确类型和适用范围；反思能够区分用户意图与宿主政策；执行日志能够完整还原工具及权限过程。** 随后处理临时例外、候选整理和专业结果校验，最后验证方法经验是否真正改善新任务。

目前已观察到跨任务个性化，但尚不能证明可靠的自主进化。继续增加反思次数、扩大画像或换更复杂的检索，可能放大已有问题。当前最有价值的工作是把现有闭环做可信、可解释、可回归。

本报告延续[原优化方案](personal-assistant-optimization-plan.md)，以最新包结构和本轮证据明确后续范围；历史方案中的实现状态不作为当前状态。详细实验材料见[实验报告](../../experiments/personal-assistant/REPORT-multiturn-2026-10-15.md)及[结构化分析](../../experiments/personal-assistant/results/multiturn-analysis-2026-10-15.json)。

## 证据与判断边界

实验覆盖项目经理、财务、教师、日常管理四类用户，两组各执行学习、单次例外、新任务迁移三个任务，每任务四轮。持续记忆组继承记忆，重置组每任务清空。共24个任务、96轮交互、12次反思；36个原生会话确认实际模型为 `opencode-go/deepseek-v4.1-flash`。主实验原生费用记录约 $0.092919。

| 已观察到的结果 | 可以支持的判断 | 尚不能支持的判断 |
|---|---|---|
| 持续记忆组恢复分节、万元精度、事实优先及额外缓冲要求 | 显式确认记忆能影响新会话行为 | 不经确认的隐式学习或自主方法进化已有效 |
| 96轮均正常结束 | 本轮会话执行完成 | 任务内容全部正确或用户满意 |
| 词法筛查持续记忆48/53、重置43/53 | 可作为定位问题的线索 | 总体成功率提升；规则存在误报与漏报 |
| 最终4条活跃规则、51条候选，未发现推断被错误激活 | 候选隔离在本轮有效 | 候选质量、合并能力及未来提升流程可靠 |
| 24条轨迹结构检查通过，协议对照仍发现字段丢失 | 结构检查可用但覆盖不足 | 标准日志足以完整复盘 |

每个角色每组只有一条合成轨迹，人工复核非盲。实验将“长期记住”原文交给宿主确认，任务边界也由执行器指定；运行包装混在用户消息中。受限权限策略未打通 code-mode 的 MCP 调用。因此本轮主要验证宿主记忆注入和多轮修订，不能代表真实用户长期使用、MCP自主学习、Pi真模型表现或自动任务边界识别。

## 问题、根因与改造方向

### 1. P1：规则类型在确认入口丢失，约束保护只覆盖部分真实入口

`assistant/remember.ts` 的 `rememberUserFact()` 只传 `text` 和 `evidence`，`host.remember(text)` 也没有类型参数。写入规则默认按 fact 处理，而 `memory/context.ts` 只把 constraint 类型或对应标签纳入必要约束。

因此，“上下文已保护 constraint”与“用户确认的约束受到保护”之间仍有缺口。本轮四条确认规则都落为 fact；离线6000字符拥挤反例中，四条都能被遗漏而不触发必要约束缺失。仅在复制视图中改类型即可获得保护。此为压力反例，主实验小库未实际发生预算溢出。

改造建议：

- 增加结构化确认入口，保留旧文本入口兼容。结构应表达类型、稳定键、范围、条件、来源片段与确认状态，而非继续以一个混合长段落表示全部规则。
- 一段确认语句可拆成偏好、约束、方法等多个原子提案。用户确认保存原文不等于确认模型扩展的解释；无法可靠判定的内容保留原文与待分类状态，明确报告保障范围，不能悄悄声称已获硬约束保护。
- `memory` 负责写入及选择不变量，`assistant` 负责提取，`host` 负责绑定可信来源。所有入口共用规则，MCP提出的类型不能赋予它用户确认身份。
- 为历史混合 fact 提供可预览迁移提案、原文证据和版本回退；不能把全部 fact 或偏好批量改成硬约束。

验收：从真实 `host.remember` 入口写入约束，再施加乱序、无关新事实和拥挤预算，约束必须被选中或发送前明确阻断；普通偏好仍可按预算省略。测试分母由独立标注的用户约束确定，不能从选择器的 `requiredIds` 自行推导。

### 2. P1：反思证据缺少来源分段，容易扩大作用域

本轮反思把“文本提问、约220字”等运行包装提炼成长久偏好候选，也把“信息未给全先问”概括成总是在排程前询问。这既是执行器混合输入的实验混杂，也揭示当前字符串输入和证据模型难以表达来源边界。仅追加一句“不要泛化”的 prompt 不能根治。

建议在 `session` 的经验契约中增加带来源的片段：用户正文、宿主政策、引用材料、助手输出、工具观察。片段保留记录/消息身份、来源类别与具体原文，宿主负责赋予来源，模型无权自行修改。`host.turn` 可以逐步支持结构化输入，旧字符串映射为一种明确来源，避免破坏兼容调用。

反思只把允许的来源片段用于相应类型提案：宿主政策可解释执行条件，但不能成为用户画像；助手建议可形成方法候选，不能成为用户偏好或授权；第三方观点保留归属。范围不明确时保留任务范围候选，不能自动扩大为项目或个人长期规则。

同时由宿主生成本次反思专用短别名，如 `E1/M2`，严格映射回完整记录及消息。当前一次反思因截短UUID而整批拒绝是正确行为；应减少模型抄写负担，并增加逐项诊断，不能接受模糊前缀匹配。第一阶段保留整批原子拒绝，只改善错误定位；部分接受以后单独定义事务语义。

验收：把完全相同的文字分别放入用户正文、宿主包装、第三方引用和助手建议，提案归属及可生效状态必须不同；短别名跨批次、未知别名和伪造引用被拒绝。ID存在、角色合法和原文语义支持分别检查，前两项通过不能替代第三项。

### 3. P1：ACP翻译丢失可获得信息，妨碍自迭代诊断

主实验协议中有21次权限请求，标准事件对应请求为0；17次工具的参数在后续更新到达，记录仍为空；17次非空工具结果或错误在标准记录中变为空。当前适配器只在初始 tool_call 记录参数，后续更新仅处理结束；文本提取也未覆盖嵌套 content。

改造建议：

- 在 `core` 扩展工具更新契约，区分未知参数、空参数和后续修订。按调用ID聚合，记录修订顺序；不通过延迟所有 start 事件伪装参数一开始就已完整。
- `transport-acp` 翻译嵌套内容、参数更新和权限请求/决定；保留相关ID及原生状态。无法表达的结构记录类型及制品引用，不能转成空字符串后静默丢弃。
- `session`、轨迹存储及CLI投影共同支持新事件。经验摘要使用最终已知参数，同时保留历史事件；错误结果、重复更新和未知调用ID有明确处理。
- `observability` 分别给出结构完整性、字段保真度和采集覆盖状态。用已保存协议样本作离线契约回放，比较协议中可观察内容与标准轨迹，避免由同一适配器自行证明没有丢信息。
- 继续对日志脱敏；详细证据用受控制品引用保存，不把任意协议载荷全部展开进默认日志。无法采集或发生脱敏时显式标注。

验收：冻结样本中的21次权限请求均可关联到决定或明确取消/错误状态；17组晚到参数及17组非空结果均可恢复。新增乱序、失败、空结果、嵌套内容及不支持内容回放，不能出现无说明的信息丢失。

### 4. P2：临时例外尚未成为确定的规则解析过程

项目经理要求“仅四列表格”，两组仍加表外文字，持续记忆组还恢复了历史分节。增加长期记忆可能增加旧习惯干扰，不能单靠强调“更了解用户”解决。

建议在发送前生成有效规则视图：来源与权限边界先固定；在用户规则内部，当前任务明确例外覆盖同一维度的历史默认，临时覆盖到期后恢复基础规则。冲突按键、范围和有效期解析，不能依赖把新旧文本都堆给模型。未知冲突影响本次结果时才澄清。

将“仅表格”等机器可检验要求同时交给输出验证器。例外遵循和默认恢复分别评测。结构化有效期、偏好更新及检索专项仍按[记忆清单](memory-optimization-backlog.md)推进，本阶段先提供接口与反例，不宣称专项已完成。

### 5. P2：反思持续增加候选，没有验证可复用经验

51条候选含重复、中英改写和泛化表述。现有反思输出主要是文本及证据ID，缺少与已有规则比较后的操作决策。

建议反思返回新增、补证据、合并、更新、临时覆盖、冲突、不保存等提案，并引用目标规则版本。确定性同键去重先行，语义合并仅生成提案，防止同主题不同受众被误合并。重复处理同一证据批次应幂等，冲突版本使用当前仓库的版本检查处理。

用户规则与方法经验采用不同提升条件：前者关注真实意图、范围和确认；后者关注独立任务效果、失败条件和可撤回版本。记忆里的方法条目不同于已经验证的可执行技能，更不同于修改助手代码。通过一次任务或重复出现不能直接提升为有效经验。

验收：同一批反思重复三次不增加等价有效条目；不同受众不误合并；排程方法在保留任务和变式上通过独立检查后才试用。移除该方法后若表现没有变化，只能报告基础能力保持，不能报告学习收益。

### 6. P2：个性化有效，但专业正确性缺少独立验收

本轮出现“10:35完成、10:40截止”却写无缓冲、压缩方案时长矛盾、到账未知却输出现金结余，以及从少量抄写错误推断能力掌握。记忆遵循无法代替这些检查。

建议通过轻量 `TaskValidator` 接口接入独立检查，先交付排期、金额/单位和输出格式三类。输入包含任务材料、结构化事实及来源、有效规则、完整草稿；输出包含覆盖范围、通过/失败/无法判定、问题位置和建议动作。未覆盖或缺数据必须显示为未知，不能计为通过。

确定性检查优先，复杂语义按需复核，不默认每轮加一次模型调用。检查完整正文、替代方案、表格和摘要；计算正确与输入口径正确分开判断。到账未确认的现金结果只能作为明确条件下的计算；学生能力结论需额外证据。

短期检查失败采用有上限的修订或澄清，避免无限反思；保存修订前后版本及检查结果。验证器只处理已声明的覆盖范围，不能给整个回答盖“事实正确”的章。

### 7. P2：MCP网关与交互提问需要单独打通

本轮受限权限处理器只允许记忆工具名，但引擎通过 execute 包装调用，外层请求被拒绝。预检中 question 工具被拒后会话取消。它们属于当前实验策略与引擎能力映射问题，不能据此判断默认CLI同样失败。

应区分外层执行能力与实际内部工具权限，优先使用能够验证内部调用及参数的路径。如果宿主无法核验包装内能力，应明确标记该配置不支持此通道；不能通过全局允许 execute 来声称实现了仅记忆授权。增加允许记忆、拒绝越界调用的正反用例。

提问方面先把普通文本澄清作为稳定路径；需要原生交互时，在能力协商后提供宿主用户交互接口，区分提问、待回答、回答、取消和超时。无人实验使用脚本化回答源，真实交互等待实际用户输入，不能由模型替用户确认。

## 实施顺序与包边界

继续使用现有17包结构，先在已有职责内补接口；不为每个问题新增子包，也不要求重写 harness。

| 阶段 | 交付与主要落点 | 阶段退出条件 |
|---|---|---|
| A：可观察、可保护 | `core`工具更新契约；`transport-acp`协议翻译；`session`记录；`observability`保真检查；`assistant`/`host`结构化确认；`memory`类型与预算不变量 | 真实确认入口压力反例不再静默遗漏约束；冻结协议字段可还原；原有接口及隔离规则不回归 |
| B：可解释地学习 | `session`来源片段；`host`结构化输入；`assistant`证据别名与提案诊断；`memory`临时覆盖、幂等更新和作用域规则 | 来源对照不串归属；未知引用拒绝；单次例外遵循并恢复；同批证据重放幂等 |
| C：结果可验收 | `evaluation`声明通用检查契约；`host`按需编排；专业实现由注入实现承载；ACP权限和交互能力验证 | 本轮排期/金额/格式反例覆盖；未知事实不被当已知；MCP正反权限案例通过；费用和修订次数可审计 |
| D：证明进化收益 | `memory-evolution`经验候选门控；实验目录补盲评、变式与移除对照 | 新任务质量改善且约束及客观质量不退化；无收益或收益不稳定时保留候选，不自动扩大使用 |

依赖顺序：先A恢复诊断可信度和规则保障，再B完善学习对象，C建立任务验收，最后D评估学习收益。A内部可分别实现日志与类型链路，但应独立提交和验收，便于定位回归。

领域规则继续在 `memory`，持久化事务沿用 `memory-file`，不在适配器内复制；`host`负责装配，`assistant`负责提示及提案编排。现有文件锁、版本校验和日志恢复能力继续复用，不因旧清单仍写着“待解决”而重复建设。专业校验不得反向让纯领域包依赖OpenCode或文件系统。

## 日志应如何支撑自迭代

一次结果不符合预期，应能顺着同一任务、轮次和版本定位到以下环节：

| 环节 | 必须能回答的问题 |
|---|---|
| 输入与证据 | 哪段来自用户，哪段是宿主政策或引用？后续纠正对应哪条原结论？ |
| 写入 | 提取了什么类型/范围，是否确认，接受或拒绝的原因是什么？ |
| 解析与检索 | 哪些规则适用、覆盖、过期或冲突？查询命中什么，未选中因何？ |
| 实际注入 | 最终提供哪些版本，是否完整包含独立标注的必要约束？ |
| 执行 | 实际模型、工具最终参数、结果、权限决定及未知信息是什么？ |
| 答案验收 | 哪些部分检查过，发现何种错误，修订是否有效？ |
| 学习提案 | 为什么新增/合并/拒绝，依赖哪些证据及评测，如何撤回？ |

所有分析区分“未写入、未生效、未召回、未注入、未遵循、规则本身错误、验证覆盖不足”。不要只显示记忆命中率或执行成功率。日志同时记录模型、策略/数据版本、预算、用量和费用缺失状态，才能比较迭代效果。

## 验证计划与放行标准

第一步无需新增模型费用：把本轮压力反例、协议样本、来源对照和答案错误固化为回归测试。运行包级测试、类型检查与依赖规则检查；样本脱敏并最小化，不提交本机完整会话数据库。

第二步复跑同一冻结24任务，比较修复前后机制表现。这些是已知回归案例，不能再称未见测试。保留重置组，单独报告个性化、客观质量、例外、冗余澄清、反思质量及总成本，不合成一个混淆问题的总分。

第三步增加未参与开发的新材料：四类用户每组至少三条独立轨迹，平衡执行顺序；不支持固定随机种子时记录重复编号及模型/引擎版本。盲化组名，由独立评分者复核主观项。受限预算下可先做一类用户试点，但如实报告样本数。

额外建立“无跨任务记忆、仅显式确认、加入反思候选”消融；方法经验再做激活/移除对照。各组固定策略与材料并记录工具差异。反思候选组不能仅因存下更多条目就视为学习有效。

| 放行维度 | 建议标准 |
|---|---|
| 约束与来源 | 冻结回归中无静默约束遗漏、无第三方/宿主政策被提升为用户规则；不因格式合法而绕过语义支持 |
| 观测完整性 | 冻结协议的可观察字段全部映射或明确标记不支持；结构完整与语义保真分开验收 |
| 任务质量 | 已知排期、口径、摘要及格式反例通过；迁移改善不能以客观错误增加换取 |
| 用户负担 | 在统一反馈规则下报告实质纠正与多余追问；固定脚本轮数不冒充真实用户负担 |
| 效率 | 同时报告主交互、反思、验证、重试的总费用与耗时，缺失账目独列；先建立同条件基线再约定阈值 |
| 可回退 | 提案、激活规则和策略均可定位版本；关闭新增机制后能回退到已知基线，旧数据不被不可逆覆盖 |

以上“无遗漏/无错误”限于声明的回归集合，不代表对所有未来任务的可靠性保证。结果不明确时扩大观察，不把一次通过当成经验推广依据。
